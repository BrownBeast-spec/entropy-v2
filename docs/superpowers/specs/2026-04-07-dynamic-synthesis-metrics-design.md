# Dynamic Query-Aware Synthesis Metrics Design

Date: 2026-04-07
Status: Draft approved for planning
Owners: API + Frontend workspace/report flows

## Problem

The Intermediate Report metric cards are static and often show zero values during report regeneration. This makes the synthesis phase feel inert and undermines trust in the report generation UX.

Current issues:

- Metric labels are static and not query-aware.
- Values can remain zero while synthesis is running.
- Icons add visual noise and do not communicate data confidence.
- No distinction between graph-derived values and heuristic/estimated values.

## Goals

1. Replace static metric labels with query-aware labels generated by LLM guidance.
2. Show dynamic, non-zero metric values while synthesis is in progress when graph evidence exists.
3. Support explicit estimates (`~value`) when values cannot be computed directly.
4. Remove icons from metric cards.
5. Keep synthesis resilient: metric generation failure must not block section generation.

## Non-Goals

- No redesign of the full report layout outside metric-card behavior.
- No mandatory SSE migration for report generation in this iteration.
- No persistence model overhaul beyond adding metric fields to report objects.

## UX Behavior

### During synthesis/regeneration

- Cards display immediately with dynamic values based on current graph snapshot.
- Values animate (count-up) until they reach target values.
- If a value is estimated, display with `~` prefix and a subtle `Estimated` hint.
- If value is computed from graph, display without prefix.
- Provisional label policy:
  - during regeneration start, labels use deterministic mode template labels
  - after API returns, labels are replaced atomically with query-aware planned labels
  - no mid-flight per-card label swaps

### After synthesis completes

- Cards lock to finalized values returned with synthesis output.
- Labels remain query-aware and mode-aware (Researcher/Strategist).

### Visual style

- Remove icon block from each metric card.
- Preserve existing card typography and spacing hierarchy where possible.

## Data Contract Changes

## `MetricCardData`

```ts
type MetricConfidence = "computed" | "estimated";

type MetricCardData = {
  key: string;
  label: string;
  value: number;
  confidence: MetricConfidence;
  rationale?: string;
};
```

## Report extension

```ts
type Report = {
  // existing fields
  metrics?: MetricCardData[];
};
```

## Synthesise response extension

`POST /api/causaly/synthesise` will return:

```json
{
  "sections": [...],
  "metrics": [
    {
      "key": "druggable-targets",
      "label": "Druggable Targets with Evidence",
      "value": 14,
      "confidence": "computed",
      "rationale": "Protein nodes with targeting evidence"
    }
  ]
}
```

If metric planning fails, API still returns `sections` and MUST return deterministic fallback metrics.

Contract rule: response MUST always include `metrics: MetricCardData[]` with exactly 4 items.

## Hybrid Metric Generation Architecture

## 1) Compute graph facts (deterministic)

Generate a compact fact map from current graph snapshot, e.g.:

- node counts by type
- unique pathways/mechanisms count
- trials count
- safety signal count
- source distribution

These are authoritative computed values.

GraphFacts contract:

```ts
type GraphFacts = {
  affectedPathways: number;
  druggableTargets: number;
  clinicalTrials: number;
  safetySignals: number;
  patentCount: number;
  competingCompanies: number;
  indiaRelevantSharePct: number; // 0..100 integer
};
```

Computation rules:

- `affectedPathways`: unique pathway tokens from node metadata.
- `druggableTargets`: protein nodes with `metadata.druggable===true`.
- `clinicalTrials`: nodes where `type==="trial"`.
- `safetySignals`: nodes sourced from safety-oriented feeds (current: `OpenFDA`).
- `patentCount`: nodes where `type==="patent"`.
- `competingCompanies`: nodes where `type==="company"`.
- `indiaRelevantSharePct`: `round(indiaRelevantNodes/totalNodes*100)`, 0 when total is 0.

Normative `isIndiaRelevant(node)` rule:

- `true` if `node.indiaRelevant === true`
- else `true` if `node.metadata.indiaContext` exists and is a non-empty object
- else `false`

## 2) LLM metric planner (labels + mapping)

Use LLM to produce query-aware metric intents constrained to 4 cards:

- preferred label text
- target fact key (when computable)
- estimated value (only if no fact key exists)
- concise rationale

LLM output is structured and validated.

Planner timeout budget:

- hard timeout: 1200ms
- on timeout, skip planner and use deterministic fallback templates

Planner output schema:

```ts
type FactKey =
  | "affectedPathways"
  | "druggableTargets"
  | "clinicalTrials"
  | "safetySignals"
  | "patentCount"
  | "competingCompanies"
  | "indiaRelevantSharePct";

type PlannedMetric = {
  key: string; // kebab-case, max 40 chars
  label: string; // 1..36 chars
  factKey?: FactKey;
  estimatedValue?: number; // integer 0..100000 when factKey absent
  rationale?: string; // max 120 chars
};
```

Validation rules:

- Exactly 4 planned metrics.
- `key` required and unique.
- `label` required and unique.
- `factKey` preferred. If absent, `estimatedValue` required.
- Invalid entries are dropped and replaced from deterministic fallback templates.
- Replacement ordering rule: fill invalid/missing slots left-to-right from mode template order.
- Duplicate-key rule: if planner returns duplicate keys, resolver rewrites duplicates with deterministic suffix (`-2`, `-3`, ...) before final output.

## 3) Resolver + sanitizer

For each metric intent:

- If `factKey` maps to computed fact => `confidence: computed`, use computed value.
- Else use `estimatedValue` => `confidence: estimated`.
- Sanitize values:
  - integer
  - min 0
  - clamp max 100000
  - `NaN`/invalid -> fallback template value

## 4) Fallback path

If LLM planner fails/timeout/invalid output:

- Use deterministic mode-specific metric templates with computed values.
- Mark non-computable values as estimated only when necessary.

This fallback guarantees non-blocking synthesis.

Deterministic fallback templates (always 4 cards):

- Researcher:
  1. `affected-pathways`
  2. `druggable-targets`
  3. `clinical-trials`
  4. `safety-signals`
- Strategist:
  1. `patent-count`
  2. `competing-companies`
  3. `india-relevant-share`
  4. `clinical-trials`

For empty graphs, all fallback values are `0` with `confidence: computed`.

Confidence mapping for fallback templates:

- all fallback values listed above are `computed` from `GraphFacts`.

## Frontend Integration

## `WorkspaceView`

- During `handleRegenerateSynthesis`:
  - set regeneration state
  - compute provisional metrics immediately from current graph
  - pass `isRegenerating` and provisional metrics to report panel
- On synthesis success:
  - persist report sections and `report.metrics`
- Merge/flicker rule:
  - provisional metrics are shown only while `isRegenerating=true`
  - once API response arrives, replace the full metric array atomically with `report.metrics`
  - no per-card merge to avoid race-induced mixed states
- On failure:
  - deterministic precedence:
    1. keep prior persisted `report.metrics` if present
    2. otherwise keep provisional deterministic metrics
    3. clear regeneration state and show error notice

## `IntermediateReportPanel`

- Prefer `report.metrics` when present.
- While regenerating, animate displayed numeric values to target numbers.
- Render estimated values as `~N` + `Estimated` hint.

Animation spec:

- Duration: 400ms
- Cadence: requestAnimationFrame-derived integer interpolation
- Direction: supports up/down transitions
- Interrupt policy: new target cancels prior animation and starts fresh
- Accessibility: if `prefers-reduced-motion`, disable animation and snap to target

Legacy compatibility read-path:

- if `report.metrics` is missing (older reports), derive deterministic metrics from `currentWorkspace` and current query context.
- if `currentWorkspace` is unavailable/stale, render deterministic 4-card fallback with zero values and `confidence: computed`.

## `MetricCard`

- Remove icon rendering.
- Render `label`, animated/display value, and optional confidence hint.

## Error Handling and Degradation

- Metric generation errors never fail report synthesis endpoint.
- Invalid metric payload from LLM falls back to deterministic metrics.
- Empty graph returns deterministic fallback cards with computed zeros.

## Module Interfaces

Backend (`apps/mastra-app`):

- `buildGraphFacts(graphSnapshot): GraphFacts`
- `planMetricCards({ queryText, personaMode, facts }): PlannedMetric[]`
- `resolveMetricCards({ planned, facts, personaMode }): MetricCardData[]`

Frontend (`entropy-research-hub`):

- `getProvisionalMetrics({ workspace, queryText, mode }): MetricCardData[]`
- `useAnimatedMetricValue(target, isActive): number`

## Testing Strategy (TDD)

## Backend/API tests

1. Happy path: synthesise returns sections + metric cards.
2. Validation path: malformed metric shape rejected/sanitized.
3. Degraded path: planner failure returns fallback metrics with sections.
4. Boundary cases: empty graph, zero-node graph, outlier estimate clamping.

## Frontend tests

1. Metric cards render without icons.
2. Estimated metrics render with `~` and `Estimated` hint.
3. Regeneration shows dynamic/non-zero values when computable.
4. Failure path falls back cleanly without runtime errors.

## Rollout Plan

1. Add backend metric generation and response schema.
2. Extend frontend synthesis client + report type.
3. Update report UI components (no icons, confidence hints, animation).
4. Add/adjust tests for API, context, and report rendering.

## Risks and Mitigations

- Risk: LLM hallucinated figures.
  - Mitigation: prefer fact-key mapping; mark estimates explicitly.
- Risk: UX jitter from animation.
  - Mitigation: short, bounded count-up duration and integer steps.
- Risk: additional latency.
  - Mitigation: perform metric planning inside existing synthesis flow and strict timeout/fallback.

## Acceptance Criteria

1. Metric cards are query-aware and icon-free.
2. During regeneration, cards are dynamic and non-zero when graph data supports it.
3. Estimated values are visibly marked with `~` and confidence hint.
4. Synthesise failure for metrics does not block section generation.
5. New/updated tests pass for backend and frontend touched areas.
6. Provisional labels are deterministic during regeneration and atomically replaced after response.
7. Legacy reports without `metrics` still render deterministic cards without crashes.
